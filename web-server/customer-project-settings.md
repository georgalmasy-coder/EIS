# Customer and project settings editor

Run `add-customer-settings-table.sql` from the repository root against the web
server database **before deploying** this change. The customer lookup cache now
loads `dbo.CUSTOMER_SETTINGS`, so the table is required for ordinary cache loads too.
Then run `migrate-customer-mfa-settings.sql` before deploying XML-based MFA.
It copies the latest legacy customer MFA policies only where no XML policy exists;
settings already saved in the editor take precedence. Both scripts are idempotent.
Restart the web server after migration so cached values are reloaded.

Add `/web/view?page=customer-project-settings` through the existing menu editor
and configure menu access there. The page uses the current session customer and
project; it does not offer another project selector.

One row per customer stores XML of this form:

```xml
<settings>
  <customer id="1">
    <security><mfaPolicy>OPTIONAL</mfaPolicy></security>
  </customer>
  <project id="2">
    <traceabilityMatching>
      <fuzzyEnabled>true</fuzzyEnabled>
      <minimumMatchingWords>2</minimumMatchingWords>
    </traceabilityMatching>
  </project>
</settings>
```

`SettingDefinition.ALL` supplies editor metadata, validation and fixed defaults.
Missing/invalid persisted values use those defaults; empty stopwords explicitly
disable filtering. `CustomerLookupCache.getSettings(session)` returns an immutable
snapshot with typed getters. Saving locks and rereads the
database row, merges the current scopes and clears the customer's existing cache
entry. Other projects and unknown XML elements are retained. The response reloads
the cache. Saves from a page whose selected customer/project has changed return 409.

Traceability matrix matching and matching-word highlights use the current project's
XML settings. Traceability properties are no longer read or generated by
`GlobalConfiguration`; remove old `traceability.match.*` entries from existing
properties files if present. Missing XML values use `SettingDefinition` defaults.

Login reads customer MFA policies from cached XML before a project is selected.
Across multiple customers, REQUIRED takes precedence over OPTIONAL, then DISABLED.
Global MFA mode and individual user policy retain their existing precedence rules.
The customer administration list displays the XML policy. Its legacy database column
is retained for compatibility and migration, but no longer controls web login.
Integration-server has no dependency on the new provider or settings model.

Validation:

```powershell
mvn -pl web-server -am test-compile -DskipTests -q
java -cp "web-server/target/test-classes;web-server/target/classes" com.bepa.eis.server.api.web.application.settings.CustomerSettingsTest
node --check web-server/src/main/webapp/js/pages/customer-project-settings-page.js
node web-server/src/test/js/customer-project-settings.test.mjs
java -cp "web-server/target/test-classes;web-server/target/classes" com.bepa.eis.server.api.web.application.views.basis.traceability.RequirementTextMatcherTest
java -cp "web-server/target/test-classes;web-server/target/classes;common/target/classes" com.bepa.eis.server.api.security.CustomerMfaPolicyResolverTest
```

For a database/browser smoke test: load the page with no settings row; edit and
save both categories; reload; switch projects and confirm isolation; restore
defaults; save an empty stopword list; change the project in another
tab and confirm saving the old editor returns a conflict. Confirm matching changes
affect both matrix colors and highlighted words. Check MFA at the next login with
OPTIONAL, REQUIRED and DISABLED policies, including users with several customers.
